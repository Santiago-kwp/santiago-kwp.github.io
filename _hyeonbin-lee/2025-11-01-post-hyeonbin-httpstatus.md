---

### HTTP 상태코드 개요

- 클라이언트가 보낸 요청의 처리 상태를 서버의 응답을 통해 알려줄 때 사용되는 3자리의 숫자 코드
- 클라이언트가 인식할 수 없는 상태코드를 서버가 반환하는 경우, 해당 상태코드는 상위 상태코드로 해석
    - 상위 상태코드는 상태코드의 첫번째 숫자로 판별(ex: 202 → 2xx (성공적인 요청 처리))

---

## HTTP 상태코드의 종류와 주요 상태코드

### 1XX(Informational/Provisional)

- 서버가 클라이언트의 요청을 수신하여 처리하고 있다는 것을 나타내는 상태코드
    - 서버가 HTTP 프로토콜에 따라 웹 브라우저의 요청을 처리하는 과정에서 중간 결과를 전달할 때 사용([참고 - RFC 9110](https://datatracker.ietf.org/doc/html/rfc9110#section-15))
        - 2XX, 4XX가 정규 응답 결과라면, 1XX는 중간 처리 결과에 해당
    - 현재도 사용되지만, 사용자가 직접 확인할 수는 없는 상태코드

---

### 2XX(Successful)

- 클라이언트의 요청이 성공적으로 처리되었음을 나타내는 상태 코드
- **주요 상태코드**
    - `200 OK` : 요청 처리에 성공했음을 의미
    - `201 Created`
        - 요청에 성공하여 서버에 새로운 리소스가 생성되었음을 나타냄
        - 새로 생성된 리소스의 URL은 응답의 `Location` 헤더 필드에 저장
    - `202 Accepted`
        - 요청이 접수되었으나 서버의 후속 처리가 아직 완료되지 않았음을 나타냄
        - 배치 처리(= 일괄 처리) 등에서 사용
    - `204 No Content`
        - 서버에서 요청을 성공적으로 처리했으나, 응답 메시지 본문에서 클라이언트에게 보낼 데이터가 없음
        - 응답 결과가 별도로 필요하지 않으면서 요청 처리에 성공했음을 나타낼 때 사용
        (예: 웹 문서 편집기의 ‘저장하기’ 버튼)

---

### 3XX(Redirection)

#### 개요

- 클라이언트가 보낸 요청의 처리를 완료하기 위해, 유저 에이전트의 추가 조치가 필요하다는 것을 나타내는 상태 코드

#### 리다이렉트(Redirect)

- 클라이언트의 요청 처리를 완수하는 과정에서, 처음에 요청했던 URL이 서버의 응답에 포함된 `Location` 헤더의 URL로 자동 변경되는 것
- **리다이렉트의 흐름**
    1. 클라이언트가 서버에게 요청을 전송
    2. 서버는 `Location` 헤더 필드를 포함한 3XX 응답을 클라이언트에게 전송
    3. 클라이언트가 처음에 요청했던 URL을 응답 메시지에 포함된 `Location` 헤더의 URL로 변경
    (리다이렉트)
    4. 클라이언트는 3.에서 변경된 URL에 관한 요청을 서버에게 다시 전송
    5. 요청 처리 성공 시, 서버는 응답 메시지를 통해 2XX 상태코드를 클라이언트에게 전송
    

#### **리다이렉트의 종류 - 영구 리다이렉트**

- 처음에 요청했던 URL을 `Location` 헤더의 URL로 영구 변경
    - 변경된 URL 주소는 검색엔진의 검색 대상에 포함
- 리다이렉트 수행 이후에도 메시지 본문의 데이터가 보존되는지에 따라 세분
    - `301 Moved Permanently`
        - 리다이렉트 시 요청 메서드가 `GET` 으로 변경되고 메시지 바디가 삭제될 수 있음
    - `308 Permanent Redirect`
        - 리다이렉트 이후에도 최초 요청 당시의 요청 메서드와 메시지 바디를 유지

#### **일시 리다이렉트 - 302, 303, 307**

- 처음에 요청했던 URL을 `Location` 헤더의 URL로 일시 변경
    - 변경된 URL은 검색엔진의 검색 대상에서 제외
- **PRG(Post-Redirect-Get) 패턴**
    - 새로고침 등으로 인해 동일한 POST 요청을 중복 전송하는 것을 방지하기 위한 패턴
    - POST 요청을 GET 요청으로 변경함으로써 새로고침해도 POST 요청에 관한 결과 화면만 조회
- 302의 모호함을 해결하기 위해 303, 307 상태코드가 등장
    - `302 Found`
        - `Location` 헤더의 url로 리다이렉트 시 요청 메서드가 `GET`으로 변경되는 것으로 간주
        - **PRG(Post-Redirect-Get) 패턴**에서 `POST` 요청을 `GET` 요청으로 변경할 때 주로 사용
    - `303 See Other`
        - `Location` 헤더의 url로 리다이렉트될 때, 요청 메서드는 항상 `GET`으로 변경
        → 기존
    - `307 Temporary Redirect`
        - `Location` 헤더의 url로 리다이렉트된 후에도 기존 요청 메서드와 메시지 본문을 유지

#### 기타: 추가 처리가 필요한 상태

- 리다이렉트에 해당하지는 않지만, 클라이언트 측의 추가 처리가 필요함을 나타내는 상태코드
- `300 Multiple Choices`
    - 클라이언트가 요청한 URL에 대해, 서버가 전송 가능한 리소스가 여러 개라는 것을 의미
        - 파일 이름은 같으나 확장자가 다르거나, 사용 언어가 다른 경우
        - 서버가 클라이언트에게 이 상태코드로 응답하면, 클라이언트에서는 요청한 리소스가 무엇인지 정확히 식별 가능한 정보를 포함한 요청을 재전송
    - 웹에서는 현재 거의 사용되지 않는 상태 코드
        - HTTP 요청 메시지의 콘텐츠 협상 헤더(이름이 `Accept`로 시작하는 헤더)를 사용하는 방식으로 대체
        - 즉, 처음에 요청 메시지를 보낼 때부터 리소스를 정확히 식별 가능한 정보를 함께 전달
- `304 Not Modified`
    - 클라이언트가 요청한 서버의 리소스가 최근에 변경된 적이 없다는 것을 나타내는 상태코드
    - 서버로부터 리소스를 가져오는 대신 HTTP 캐시에 저장된 리소스를 사용할 수 있다는 의미
        - 최초 요청 시 GET, HEAD 메서드를 사용한 경우

### 4XX(Client Error)

- 클라이언트 측의 잘못된 요청/데이터 송신으로 인해 서버의 요청 처리가 실패했음을 나타내는 상태 코드
→ 동일한 요청 메시지를 재전송해도 무조건 실패
- **주요 상태코드**
    - `400 Bad Request`
        - 클라이언트가 잘못된 요청을 전송하여 서버가 요청을 처리할 수 없음을 나타내는 상태 코드
        - 요청 구문, 메시지 형식 등에서의 오류가 주요 원인 → 클라이언트에서 전송한 요청 재검토 필요
    - `401 Unauthorized`
        - 요청한 리소스를 클라이언트가 사용하려면 인증이 필요하다는 것을 나타내는 상태 코드
        - 401 상태코드 전송 시, `WWW-Authenticate` 헤더를 포함시켜 인증 방법에 관한 정보도 제공
    - `403 Forbidden`
        - 서버가 요청을 이해했지만 승인을 거부했음을 나타내는 상태코드
        - 클라이언트가 인증 절차는 통과했으나, 리소스에 접근하기 위한 권한을 갖추지 못한 경우
    - `404 Not Found`
        - 요청한 리소스를 서버에서 찾을 수 없거나, 리소스 접근 권한이 없는 클라이언트로부터 리소스를 숨겼음을 나타내는 상태코드

---

### 5XX(Server Error)

- 오류의 원인이 서버에게 있음을 나타내는 상태 코드
- 클라이언트의 요청에는 이상이 없다고 할 때, 서버 측의 문제로 인해 요청 처리에 실패했음을 나타내는 상태 코드
    - 동일한 요청 메시지 재전송 시 요청 처리 성공 가능성 존재
    (요청을 다시 보내는 동안 서버가 복구될 수도 있기 때문)
- **주요 상태코드**
    - `500 Internal Server Error`
        - 서버 내부 문제로 인해 오류가 발생하여 요청을 처리할 수 없음을 의미
        - 서버 측 오류이지만 특정한 5XX 상태코드로 식별하기 애매한 경우에도 사용
    - `503 Service Unavailable`
        - 과부하 등의 요인으로 인해, 서버가 일시적으로 클라이언트의 요청을 처리하지 못하게 된 상태
        - 응답 시 `Retry-After` 헤더 필드를 통해 클라이언트에게 리소스 사용 가능 시점 안내 가능
