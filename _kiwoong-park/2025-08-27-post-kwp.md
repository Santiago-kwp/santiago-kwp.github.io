### 학습 목표 : 프로세스의 정의 이해, 프로세스의 상태 분류, 인터럽트 정의 및 문맥 교환의 이해

### 학습 내용 요약 :

- job 은 프로그램과 데이터로 정의하며, 커널에 등록된 작업을 프로세스라고 함. 즉, 능동적인 개채가 프로세서이고, 프로세서에 의해 사용, 반환되어지는 수동적인 모든 개체를 자원으로 정의함.
- 프로세스 관리 블록(PCB)은 커널 영역에 있는 프로세스를 관리하기 위한 식별 번호를 포함하는 것으로 프로세스 상태 정보, 우선순위 정보 등이 포함됨
- 프로세스의 상태는 메모리 할당 유무에 따라 Ready, Running, Asleep/Block, Terminated ↔ Suspended ready, Suspended Asleep/Blocked로 크게 나눌 수 있음. 기타 자원의 할당 유무에 따라 Ready ↔ Asleep으로 구분 가능함.
- 인터럽트는 예상치 못한 외부의 개입으로 인한 프로세스 중단을 의미하며, I/O, clock, machine check interrupt 등의 다양한 원인으로 인터럽트가 발생할 수 있다.
- 인터럽트 처리를 위해 현재 진행하던 프로세스의 상태 중 프로세서 안에 있는 레지스터에 있는 정보인 CPU register context 정보를 메모리의 PCB에 저장하는 과정을 context saving, 역 과정을 context restoring 이라고 하며 통틀어서 context switching 이라고 한다.
- context switching에는 상당한 비용이 발생하며 OS 별로 다르고, 불필요한 context switching을 줄이는 것이 중요하다.

### Job/Program vs Process

- Job/Program : 실행할 프로그램(작업) + 데이터
  - 컴퓨터 시스템에 실행 요청 전의 상태
- Process : 실행을 위해 시스템(커널)에 등록된 작업
  - 시스템 성능 향상을 위해 커널에 의해 관리된다.
  - 메모리를 할당 받았을 때

![lec3_jobvsProcess.png](/assets/images/lec3_jobvsProcess.png)


### 프로세스의 정의

> 간단히만 정의하자면 실행 중인 프로그램
>
- 커널에 등록되고 커널의 관리 하에 있는 작업
- 각종 자원들을 요청하고 할당받을 수 있는 개체
- 프로세스 관리 블록(PCB)을 할당 받은 개체
- 능동적인 개체(active entity)

> PCB (프로세스 관리 블록, Process Control Block)
>
- 커널 공간 내에 존재
- 각 프로세스 들에 대한 정보를 관리

### 자원의 개념

> 커널의 관리 하에 프로세스에게 할당, 반납되는 수동적인 개체 (passive entity)
>
- 자원의 분류
  - H/W : Processor, Memory, disk, monitor, keyboard, etc
  - S/W : Message, signal, files, installed S/Ws, etc

### Process Control Block

- 커널 영역 안에 존재하며 프로세스 관리에 필요한 정보를 저장한다.
- 각 프로세스들에 대한 상태 정보를 저장

![lec3_pcb.png](/assets/images/lec3_pcb.png)
### PCB가 관리하는 정보

- PID : 프로세스 고유 식별 번호
- 스케쥴링 정보 : 프로세스 우선순위 등과 같은
- 프로세스 상태 : 자원 할당, 요청 정보 등
- 메모리 관리 정보 : page table, segment table
- 입출력 상태 정보 : 할당 받은 입출력 장치, 파일 등에 대한 정보
- 문맥 저장 영역 (context save area) : 프로세스의 레지스터 상태를 저장하는 공간
- 계정 정보 : 자원 사용 시간 등 관리

### 프로세스의 상태

Created State

- 작업을 커널에 등록
- PCB 할당 및 프로세스 생성
- 커널의 입장에서 가용 메모리 공간 체크 및 프로세스 상태 전이
  - Ready or Suspended ready

Ready State

- 프로세서 외 다른 모든 자원을 할당 받은 상태
  - 프로세서 할당 대기 상태
  - 즉시 실행 가능 상태
- Dispatch (Schedule)
  - Ready State → Running State로 전이되는 것을 디스패치 혹은 스케쥴이라고 명명함

Running State

- 프로세서와 필요한 모든 자원을 할당 받은 상태
- Preemption
  - Running State → Ready State
  - 프로세서 스케쥴링 (e.g. time-out (시분할), priority changes)
- Block/Sleep
  - 회사에 왔는데 필요한 서류를 집에 놓고 왔네… ⇒ I/O 등 자원 할당 요청을 해야해서 잠깐 멈춤
  - Running State → Asleep State

Blocked/Asleep State

- 프로세서 외 다른 자원을 기다리고 있는 상태
  - 자원 할당은 시스템 콜에 의해 이뤄짐
- Wake-up
  - Asleep → ready State

Suspended State

> 메모리가 없는 상태
>
- 메모리를 할당 받지 못한(뻇긴) 상태
  - 메모리 image를 swap device에 보관 ( 작업을 하다가 중간에 상태를 저장을 해야하니깐, 저장 후 다시 메모리를 할당 받으면 저장했던 상태부터 다시 시작할 수 있음)
    - 메모리 image : 특정 시간의 메모리의 상태
    - swap device : 프로그램 정보 저장을 위한 특별한 파일 시스템
    - swap - out : suspended ⇒ 메모리 이미지를 스왑 디바이스에 저장
    - swap - in : resume (재개) ⇒ 스왑 디바이스에 저장된 메모리 이미지를 복원시켜 작업 재개
  - 커널 또는 사용자에 의해 발생

Terminated / Zombie State

- 프로세스 수행이 끝난 상태
- 모든 자원 반납 후, 커널 내에 일부 PCB 정보만 남아 있는 상태
  - 이후에 비슷한 작업이 왔을 때 쉽게 비슷한 프로세스를 관리하기 위해서 정보를 수집

![lec3_processStateTransition.png](/assets/images/lec3_proessStateTransition.png)

### 프로세스의 상태 정리

| 프로세스 상태명 | 프로세서 할당 유뮤 | 메모리 할당 유무 | 기타자원 할당 유무 |
| --- | --- | --- | --- |
| Ready | X | O | O |
| Running | O | O | O |
| Asleep/Block | X | O | X |
| Suspended ready | X | X | O |
| Suspended blocked | X | X | X |


### 프로세스 관리를 위한 자료 구조

> 프로세스의 상태 별로 각각 큐형 자료 구조가 존재
>
- Ready Queue : 스케쥴러에 의해 관리됨
- I/O Queue : 자원에 따라 각각 관리됨
- Device Queue : 자원에 따라 각각 관리됨

### 인터럽트

> 예상치 못한, 외부에서 발생한 이벤트
>

인터럽트의 종류

- I/O, Console, Program check, Machine check, Inter-process, System call, clock interrupt 등이 있음

### 인터럽트 처리 과정

인터럽트 발생 → 프로세스 중지 (커널 개입) → 인터럽트 처리(interrupt handling) → 인터럽트 발생 장소, 원인 파악 → 인터럽트 서비스 할 것인지 결정 → 인터럽트 서비스 루틴 호출

- 프로세스 중지 시 context saving 이 일어나며 해당 context가 PCB에 저장됨
- 다시 저장된 프로세스가 수행될 때 context restoring이 일어나며 프로세서의 할당을 받음

### Context Switching

context : 프로세스와 관련된 정보 집합

- CPU register context  ⇒ in CPU
- Code & data, Stack, PCB ⇒ in Memory
- interrupt 가 발생되면 CPU에서 작업이 빠지는 것이므로 CPU register context가 메모리에 저장된다.

context saving : 현재 프로세스의 register context를 저장하는 작업

context restoring : 메모리에 있던 register context를 다시 CPU register에 가져다 놓는 것

> context switching : 실행 중인 프로세스의 context를 saving하고, 앞으로 실행할 프로세의 context를 restoring 하는 것 ⇒ 커널의 개입을 통해 이뤄진다
>

### Context switching overhead

- Context switching 에 소요되는 비용
  - OS 마다 다름
  - OS의 성능에 큰 영향을 준다
- 불필요한 Context switching 을 줄이는 것이 중요
  - 예) 쓰레드의 사용
