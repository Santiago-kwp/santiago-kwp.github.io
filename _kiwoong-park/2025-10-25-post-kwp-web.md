### 참고 자료 : IT 원리의 기본이 되는 네트워크 구조 원리 교과서(feat. 밀리의 서재)

### 순공부 시간 : 25.10.25 1005 ~ 1020 (15분), 1029 ~ 1104 (35분), 1122 ~ 1142 (20분), 1940 ~ 2030 (50분), 2057 ~ 2132 (35분), 2147 ~ 2246 (59분)

### 학습 목표 : 서버 클라이언트 통신을 이해하기 위한 기초 인터넷 네트워크 기초 개념 이해

### 학습 내용 요약

- 인터넷을 통한 클라이언트와 서버간 데이터 통신 과정

  1. 클라이언트의 웹 브라우저로 요청 URL 입력
  2. 웹 브라우저는 URL 의미 조사 -> 요청 메시지 생성 -> 프로토콜 스택을 통해 메시지 송신
  3. TCP/IP 패킷으로 변환 후 전기 신호로 변환해 LAN 케이블로 보냄 (소켓 통신 진행)
  4. 허브/스위치/라우터 등을 통해 프로바이더에게 전달되고 프로바이더가 서버쪽으로 패킷을 옮겨줌
  5. 방화벽 점검, 캐시 서버 전달
  6. 웹 서버에 패킷 도착 -> 메시지 복원

- IP 주소는 네트워크/호스트 번호로 구분됨.

  - IP 프로토콜은 비연결성, 비신뢰성, 프로그램 구분X (포트를 통해)

- TCP 세그먼트 : 출발지 port, 목적지 port, 전송제어, 순서, 검증 정보 포함

  - 연결지향 : 3 way handshake
  - 데이터 전달 보증
  - 순서 보장
  - 신뢰할 수 있음

- DNS : 도메인명 서비스로 도메인이름에 매핑되는 IP 주소를 반환해줌
  - 사용 목적 : 도메인명의 데이터가 IP주소에 비해 훨씬 크기 때문에 네트워크 부하를 줄이고 속도 상승 목적
  - 도메인명은 계층적으로 구분되며, 루트 DNS 서버가 존재함.

> 핵심 질문 : 인터넷에서 컴퓨터 둘은 어떻게 통신할까?

클라이언트 ↔ 서버

- 클라이언트는 클라이언트의 웹 브라우저를 통해서 특정한 요청(Request)을 웹 서버에 발송
- 웹 서버는 요청에 따라 움직임. 결과(응답)을 클라이언트의 웹 브라우저로 보낸다.
- 웹 브라우저와 웹 서버 간 주고 받는 요청이나 응답을 상대측으로 옮겨주는 시스템이 필요하다.

1. 웹 브라우저

브라우저에 URL 입력 : Ex. http:www.test.com/index.html

→ 브라우저는 정해진 규칙에 따라 URL의 의미 조사

→ 의미에 따라 요청 메시지 생성 : “index.html” 이라는 파일에 저장된 페이지의 데이터를 주세요
→ 브라우저는 OS에 내장된 네트워크 제어용 소프트웨어에 의뢰해 메시지를 서버쪽으로 보내달라고 함

1. 프로토콜 스택, LAN 어댑터

OS에 내장된 프로토콜 스택( : 네트워크 제어용 소프트웨어)의 역할

- 브라우저가 보낸 메시지를 패킷 안에 저장해, 받는 이의 주소 같은 제어 정보 부가(ex. 편지를 봉투에 넣고, 받는 이의 이름을 쓴다)
- 통신 오류 시 패킷 다시 보내거나, 데이터 송신 페이스 조절 등

→ 패킷을 LAN 어댑터(이더넷, 무선 LAN 통신 시 사용하는 하드웨어)에 보냄

→ LAN 어댑터가 패킷을 전기신호로 변환해 LAN 케이블로 보냄

→ 패킷이 네트워크 안으로 들어감

1. 허브, 스위치, 라우터

LAN 어댑터가 송신한 패킷은 스위칭 허브를 거쳐 인터넷 접속용 라우터로 보냄

→ 라우터의 끝은 이미 인터넷으로, 프로바이더가 패킷을 상대에게 옮겨다 줌

1. 접근 회선, 프로바이더

인터넷 입구에는 접근 회선이라는 통신 회선 존재 (인터넷 접속 통신 회선 총칭)

→ 접근 회선은 계약한 프로바이더에 연결

→ POP (Point Of Presence) 설비 존재 : 프로바이더 전용으로 만들어진 라우터

→ POP에서 전 세계로 배송 → 다수의 프로바이더와 다수의 라우터를 거쳐 전달

1. 방화벽, 캐시 서버

패킷은 최종 웹 서버 쪽의 LAN에 도달

→ 방화벽 대기 : 패킷 점검

→ 캐시 서버 대기 (접속한 페이지의 데이터가 캐시에 있으면 캐시에서 줌, 부하 분산 역할, 콘텐츠 배포 서비스 등)

1. 웹 서버

도착한 패킷의 내용물 추출해 원래의 요청 메시지 복원

→ 웹 서버 애플리케이션에 건냄 (웹 서버 OS에 내장된 프로토콜 스택이)

→ 웹 서버 애플리케이션이 요청 메시지의 의미를 읽음

→ 메시지에 적힌 지시 내용에 따라 데이터를 응답 메시지에 넣어 클라이언트에게 반송

## 인터넷 네트워크

- 인터넷 통신
- IP(Internet Protocol)
- TCP, UDP
- PORT
- DNS

### 인터넷 통신

- 클라이언트 - 서버
- OSI 7 계층

  - 물리 계층 : 비트
  - 데이터 링크 계층 : 프레임
  - 네트워크 계층 : 패킷
  - 전송 계층 : 세그먼트

- 클라이언트 ↔ 인터넷 망 ↔ 서버

### IP

- 네트워크 계층에서 IP 헤더가 붙는다.
- 지정한 IP 주소에 데이터 전달
- 패킷이라는 통신 단위로 데이터 전달
- IPv4 기준 32비트(8비트 \* 4)

IP는 네트워크 상의 주소로 도로명에 해당하는 번호를 네트워크 번호, 건물 번호에 해당하는 번호를 호스트 번호라고 한다.

- 네트워크 번호와 호스트 번호를 합쳐 32비트
- 네트워크를 구축할 때 사용자가 내역을 정할 수 있음
- 네트워크와 호스트 번호를 나타내는 정보를 넷마스크
- IP 주소 표기 방법
  - 10.11.12.13 (IP 주소 본체)
  - 10.11.12.13/255.255.255.0 (IP 주소 본체와 같은 방식으로 넷마스크 표현)
  - 10.11.12.13/24 (네트워크 번호의 비트 수로 넷마스크 표현)
  - 10.11.12.0/24 (서브넷 표현 : 호스트 번호 부분의 비트가 모두 0인 것은 서브넷 자체를 표현)
  - 10.11.12.255/24 (브로드캐스트 표현 : 호스트 번호의 비트가 모두 1인 것은 그 서브넷 전체에 대한 브로드캐스트 표현)
    - 브로드캐스트 : 서브넷 상에 있는 모든 기기에 패킷을 보내는 것

IP 패킷 정보

- 출발지 IP
- 목적지 IP
- 전송 데이터 및 기타
- 정상 전송 시 HTTP 200번 (OK response) → HTTP request가 성공적으로 완수됬음.

### IP 프로토콜의 한계

- 비연결성
  - 패킷을 받을 대상이 없거나 서비스 불능 상태여도 패킷 전송
- 비신뢰성
  - 중간에 패킷이 사라지면?
  - 패킷이 순서대로 안오면?
- 프로그램 구분
  - 같은 IP 를 사용하는 서버에서 통신하는 애플리케이션이 둘 이상이면?

### TCP

- 인터넷 프로토콜 스택의 4계층
- 프로토콜 계층
  - 애플리케이션
  - OS
  - 네트워크 인터페이스
  1. 프로그램이 Hello, World! 메시지 생성
  2. 소켓 라이브러리를 통해 전달
  3. TCP 정보 생성, 메시지 데이터 포함
  4. IP 패킷 생성, TCP 데이터 포함

### TCP/IP 패킷 정보

- IP 패킷 : 출발지 IP, 목적지 IP, 기타
- TCP 세그먼트 : 출발지 PORT, 목적지 PORT, 전송 제어, 순서, 검증 정보
- 전송 데이터

### TCP 특징

- 전송 제어 프로토콜 (Transmission Control Protocol)
- 연결지향 - TCP 3 way handshake (가상 연결)
- 데이터 전달 보증
- 순서 보장
- 신뢰할 수 있는 프로토콜
- 현재는 대부분 TCP 사용

### TCP 3 way handshake

1. SYN : 접속 요청
2. SYN+ACK(요청 수락)
3. ACK(\*참고 : ACK와 함께 데이터 전송 가능)

- 데이터 전달 보증
- 순서 보장

### PORT

- 한번에 둘 이상 연결해야 하면?
  - 게임, 화상통화, 웹 브라우저 요청
  - 같은 IP 내에서 프로세스 구분
- 0 ~ 65535: 할당 가능
- 0 ~ 1023 : Well Known 포트

### DNS

- 도메인 명을 IP 주소로 변환
- IP는 기억하기 어렵고, 변경될 수 있기 때문에
- 클라이언트는 가장 가까운 DNS 서버를 통해서 도메인 명에 해당하는 IP 주소를 받음.

  - 브라우저는 어떻게 DNS 서버에 질의할까?
  - DNS 서버에 질의 : DNS 서버에 질의 메시지를 보내고, 반송되는 응답 메시지를 받는다.
  - DNS 서버에 클라이언트로 작동한다 = DNS 리졸버 (resolver)
  - DNS 시스템을 사용해 IP 주소를 조회하는 것 = 이름 분석(name resolution)
  - 리졸버의 실체는 Socket 라이브러리에 들어 있는 부품화된 프로그램

    - Socket 라이브러리는 라이브러리의 일종으로, OS에 내장된 네트워크 기능을 애플리케이션에서 호출하기 위한 부품을 모은 것
    - 리졸버의 프로그램명(예. `getHostByName`) 과 웹 서버의 이름(`www.test.com`)을 쓰기면 리졸버를 호출

    ```jsx
    <application program name> (parameter) {
    	...
    	<memory area> = getHostByName("www.test.com");
    	...
    	...
    }

    ```

    - 리졸버를 호출하면 리졸버가 DNS 서버에 질의 메시지를 보냄 → DNS 서버에서 응답 메시지가 돌아옴.
    - 메시지 송신 작동은 리졸버가 직접 실행하는 것이 아니라 OS 내부에 내장된 프로토콜 스택을 호출해 실행
      - 프로토콜 스택 : OS 내부에 내장된 네트워크 제어용 소프트웨어, 프로토콜 드라이버, TCP/IP 소프트웨어
    - 프로토콜 스택에서 메시지를 보내는 작동을 실행한 후, LAN 어댑터를 통해 메시지가 DNS 서버로 송신됨.
    - 웹 서버가 DNS 서버에 등록돼 있으면 답을 찾고, 그 답을 응답 메시지에 싸서 클라이언트에 반송
    - 응답 메시지에는 IP주소가 저장 → 프로토콜 스택을 거쳐 리졸버로 건내짐 → 리졸버는 주소를 추출해 브라우저에서 지정된 메모리 영역 안에 씀.

  - DNS에 보내는 질의 메시지에는 아래의 세 가지 정보가 포함돼 있음
    - 이름 : 서버와 메일 배송처 등의 이름
    - 클래스 : DNS의 시스템이 고안됐을 때는 인터넷 이외의 네트워크 이용도 검토 ⇒ 지금은 인터넷 이외의 네트워크는 소멸하여 클래스는 항상 IN 값
    - 타입 : 이름에 어떤 타입(종류)의 정보가 대응하는지를 나타냄. 예를 들어 타입이 A면 이름에 IP주소가 대응한다는 것, MX면 이름에 메일 배송처가 대응. 이 타입에 따라 클라이언트에 회답하는 정보 내용은 다름.
    - 예시 : 이름 = [www.test.com](http://www.test.com/), 클래스 = IN, 타입 = A => IP 주소를 회답

**_DNS 를 이용하는 목적_**

- 인터넷 내부에는 라우터가 여러 개 있고, 라우터가 연계돼 IP 주소를 통해 목적지가 어디에 있는지 판단한 후 데이터를 옮기는데 IP 주소 대신 이름을 사용하면?
  - IP 주소는 32비트, 즉 4바이트인 반면, 도메인명은 최소 수십바이트에서 최대 255바이트나 됨.
  - 그만큼 라우터 부하가 늘어나고 데이터 옮기는 시간이 더 걸림

**_도메인명 계층_**

- DNS 서버에 질의 후 작동 하는 방식 : 정보를 분산해 여러 DNS 서버에 등록한 다음, 이 DNS 서버들이 연계해 어디에 정보가 등록돼있는지 찾아내는 시스템
- DNS 에서 취급하는 이름은 [`www.lab.glascom.com`](http://www.lab.glascom.com) 처럼 도트로 구분함.
- 이 도트가 계층 구분을 나타냄
- 오른쪽에 있는 것이 상위 계층을 나타냄
  - com 사업부 → glasscom 부 → lab과 → www 라고 생각할 수 있음
  - 부서 하나에 해당하는 것을 도메인이라고 부름
  - .com 이라는 도메인 아래에 glasscom이라는 도메인이 있고, 그 아래에 lab이라는 도메인, 그 도메인 아래에 www 이름이 있음.

**담당 DNS 서버를 검색해 IP 주소를 취득**

- 하위 도메인을 담당하는 DNS 서버의 IP 주소를 상위 DNS 서버에 등록
- 상위 DNS 서버의 IP 주소를 더 상위의 DNS 서버에 등록하는 식
  - [`lab.glasscom.com`](http://lab.glasscom.com) 이라는 도메인 주소를 담당하는 DNS 서버의 IP를 `glasscom.com`의 DNS 서버에 등록하고, `glasscom.com`의 DNS 서버의 IP를 `com` 도메인의 DNS 서버에 등록하는 식
- 인터넷 도메인에는 .com, .kr 위에 루트 도메인이 있음.
  - 루트 도메인을 명시적으로 쓸 경우 `www.glasscom.com.` 으로 표시함.
- 루트 도메인의 DNS 서버를 인터넷에 존재하는 DNS 서버에 모두 등록함 ⇒ 어느 DNS 서버도 루트 도메인에 접속할 수 있음
- 클라이언트에서 어딘가의 DNS 서버로 접속하면 그곳에서 루트 도메인을 거쳐 도메인 계층을 아래로 따라가다가 최종적으로 목적지 DNS 서버에 도달할 수 있음.

**_프로토콜 스택에 메시지 송신 의뢰하기_**

> OS 내부의 프로토콜 스택에 메시지 송신 작동을 의뢰할 때, Socket 라이브러리의 프로그램 모듈을 정해진 순서대로 호출한다.

- 데이터를 송수신하는 컴퓨터 사이에 데이터 통로 같은게 있고 (일종의 파이프), 송수신이 작동하기 전에 양쪽 사이를 파이프로 연결해야 한다.
- 파이프의 양 끝단 출입구를 소켓이라고 부름
- 먼저 서버쪽에서 소켓을 만듦 ⇒ 그 소켓에 클라이언트가 파이프를 연결하러 오기를 기다림 (= 서버쪽 파이프 연결)
- 클라이언트에서도 소켓을 만듦 ⇒ 이 소켓에서 파이프로 서버쪽 파이프와 서버쪽 소켓과 연결
- 데이터를 모두 보내고 나면 연결된 파이프를 떼어냄
- 요약
  - 소켓을 만든다 (소켓 생성 단계)
    - 소켓을 식별하기 위한 디스크립터 생성 (애플리케이션은 ‘디스크립터’라는 번호표로 소켓을 식별함)
  - 서버 쪽의 소켓에 파이프를 연결한다. (접속 단계)
    - 소켓 라이브러리의 connect 프로그램 모듈을 호출해 의뢰 작동을 실행
    - connect 호출 시 필요한 것 3개: 디스크립터, 서버의 IP 주소, 서버의 포트 번호
  - 데이터를 송수신한다. (송수신 단계)
    - write 호출할 때 디스크립터와 송신 데이터 지정 ⇒ 프로토콜 스택이 송신 데이터를 서버를 향해 송신
    - 서버는 수신 작동을 실행, 받은 데이터의 내용을 조회해 처리 후 응답 메시지를 보냄 → 메시지 회신 시 수신 작동
    - read 프로그램 모듈을 통해 프로토콜 스택에 수신 작동을 의뢰 ⇒ 수신한 응답 메시지를 저장하기 위한 메모리 영역을 지정 (메모리 영역 = 수신 버퍼) ⇒ 응답 메시지가 돌아오면 read 가 받아서 수신 버퍼에 저장 ⇒ 수신 버퍼에 메시지를 저장한 시점에서 메시지를 애플리케이션에 건냄
  - 파이프를 떼어내고 소켓을 종료한다.
    - 소켓라이브러리의 close 라는 프로그램 모듈 호출
    - HTTP 프로토콜에서는 서버쪽에서 응답 메시지를 다 보냈을 때 웹 서버쪽에서 종료 작동을 실행하기 때문에 웹 서버에서 close를 호출
    - 클라이언트에게 전달되고, 클라이언트의 소켓은 종료 단계에 들어감
- 이 네 단계 작동을 실행하는 것은 OS 내부의 프로토콜 스택
