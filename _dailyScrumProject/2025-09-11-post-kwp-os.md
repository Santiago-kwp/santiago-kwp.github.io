    - 첫 번째 단계는 읽을 수 있는지 독자의 수를 증가시킬 때 다른 독자가 동시에 수를 증가 시키면 안되므로 동기화 해야하는 단계와 해당 단계를 지나면 읽기를 진행하고
    - 두 번째 단계는 독자 수를 감소시켜야 할 때 역시 다른 독자가 동시에 수를 감소시키면 안되므로 동기화 해야하는 단계로, 내가 만약 마지막 독자라면 까먹지 않고 저자를 깨우는 연산을 수행해야 한다.

### Semaphore

- 초기화 연산 : S 변수에 초기값을 대입하는 연산
- P(S) 연산 : 자원이 있는지 확인하고, 들어가서 자물쇠를 잠그는 연산

    ```java
    if ( S > 0 ) {
    	S = S - 1; // 임계 영역에 아무도 없다면, 들어가서 문을 잠근다.
    } 
    else { // spinLock에서는 뺑뺑 돌면서 기다림 
    	wait on the queue Q_s // 못 들어간다면 레디 큐라는 대기실에서 기다림!
    }
    ```

- V(S) 연산 : 임계 영역에서 나오면서 자원을 반납하는 연산

    ```java
    if ( someone waiting process on Q_S ) { // 레디큐에 기다리고 있는 어떤 프로세스가 있으면
    	then wake up one of them }
    else { // 기다리는 애가 없으면 그냥 물건을 하나 돌려놓고 오자
    	S = S + 1;
    }
    ```


- 모두 individual 한 연산 ⇒ OS가 이를 보장

### 생산자 - 소비자 문제

- 생산자 프로세스 : 메시지를 생성하는 프로세스 그룹
- 소비자 프로세스 : 메시지를 전달받는 프로세스 그룹
- 생산자가 버퍼에 물건을 놓고 있을 때는 소비자가 가져가면 안되고, 소비자가 버퍼에서 물건을 가져가려고 할 때는 생산자가 물건을 놓고 있으면 안된다.⇒ 즉 버퍼는 한 번에 한 프로세스만 접근해야 한다. ⇒ 버퍼가 임계 영역임
  - 버퍼가 하나일 때의 생산자 - 소비자 문제

  ![image.png](/assets/images/lec6_PdCsProbOneBuffer.png)

  - 공유 변수 : 소비되었는지 확인하는 consumed, 생산되었는지 확인하는 produced, 버퍼
  - 생산자는 먼저 소비되었는지를 P(consumed) 연산으로 확인한다.
    - 소비가 안되었다면 레디큐에 들어가서 대기한다.
    - consumed가 되었으면 버퍼에 들어가서 버퍼에 메시지를 놓고,
    - V(produced) 연산을 통해 대기하고 있던 소비자를 깨움
  - 소비자는 먼저 생산되었는지를 P(produced) 연산으로 확인한다.
    - 생산이 안되었다면 레디큐에 들어가서 대기한다.
    - 생산이 되었으면 P(produced) 연산을 통해 버퍼에 들어가서 메시지를 받고,
    - V(consumed) 연산을 통해 대기하고 있던 생산자를 깨운다.

- n개의 버퍼일 때 생산자 - 소비자 문제
  - 생산자는 버퍼가 비었는지 확인하고 (=P(nrempty))→ 비었으면 버퍼에 들어가서 물건을 놓고 → 위치를 원형 큐에서 하나 증가 시켜주고 → 나오면서 버퍼에 물건을 하나 채우고, 하나가 찼다고 알려준다 (=V(nrfull))
  - 소비자는 버퍼에 물건이 찼는지 확인하고 (=P(nrfull)) → 물건이 있으면 버퍼에 들어가서 물건을 소비하고 → 위치를 원형 큐에서 하나 증가 시켜주고 → 나오면서 물건을 하나 줄이고, 버퍼에 물건이 하나 줄었다고 알려준다 (=V(nrempty)

### Reader - Writer 문제

- Reader 는 읽는 사람으로 여러 명이서 읽어도 된다.
- Writer는 쓰는 사람으로 한명만 와서 쓸 수 있다.
- Reader가 읽고 있을 때는 Writer가 와서 수정할 수 없다.
- Writer가 쓰고 있을 때는 Reader가 읽을 수 없다.
- 해결법 : Reader / Writer 에 대한 우선권 부여
  - Reader preference solution : 한 독자가 읽고 있을 때, 저자가 와서 쓰려고 기다리고 있었지만, 그 사이 두 번째 독자가 읽으려고 오면, 그 두번 째 독자가 읽을 수 있도록 먼저 순위를 바꿔주는 경우
  - Writer preference solution : 반대임
- Reader Preference Solution

![image.png](/assets/images/lec6_ReaderWriterProb.png)

- 생산자는 단순하게 쓸 수 있는지 확인하고 쓸 수 있다면 들어가서 문을 잠근다. (= P(wmutex))
  - 다 쓰고 나면 나오면서 소비자에게 썼다고 알려준다 (= V(wmutex))
- 소비자는 2단계 프로세스로 구분할 수 있다.
  - 1단계는 읽으려고 들어가는 사전 작업을 하는 단계로 소비자 여러명이서 하면 안되므로 P(rmutex)를 걸어준다
  - 먼저 읽고 있는 독자의 수를 체크하여 독자가 한명도 없으면 저자에게 읽을거니까 쓰지말라고 한다 (=P(rmutex))
    - 만약 읽고 있는 독자가 한 명 이상이면 굳이 저자에게 알리지 않아도 되니 넘어간다.
  - 저자를 한 명 추가 시킨다. ( 이 작업은 동시에 이뤄지면 안되므로 앞에서 P(rmutex)를 걸었다.
  - 사전작업을 마무리 하면서 다른 독자가 진행할 수 있도록 알려준다. = V(wmutex)
  - 그리고 책을 읽는다
  - 2단계는 다 읽고 나오는 단계로 독자의 수를 감소 시켜주는 것도 동기화가 되어야 하므로 P(rmutex)를 걸어준다.
  - 독자의 수를 하나 감소시키고, 만약 내가 마지막 문 닫고 나오는 독자라면 저자에게 쓸 수 있다고 알려 준다. ( = V(wmutex))
  - 해당 작업이 끝나면 다른 독자에게도 나올 수 있다고 알려준다 (= V(rmutex)

### Semaphore 의 특징

- No busy waiting : 기다려야 하는 프로세스는 block(asleep) 상태가 된다.
- Semaphore의 레디 큐에 대한 우선순위는 비결정적이다. ⇒ 기아 문제가 생길 수 있다.
